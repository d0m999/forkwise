# 跨项目剪切的目标粘贴与结果未知恢复

状态：工程采纳；Issue #45；2026-11-09 审查修复。依据 D349–D355、D466、D467 与 #45 的 AC1–AC5；不宣称未来对象或完整首版验收。

## 文档职责与适用范围

本 ADR 记录**生产实现**的字段与操作约束，作为 `AGENTS.md`「保持文档职责」中「字段与操作约束改映射契约／正式技术取舍查 ADR」的落点。

`docs/architecture/mapping-contract-v0.1/CONTRACT.md` 是参考契约：文件头明言「产品提案待确认」「不是生产迁移」，其第 1 节只描述隔离参考模型的领域定义，第 6 节的决策状态不得与本 ADR 合并。生产已实现的规则不写入该节正文；D466／D467 保留用户已确认的产品决定，工程口径在此展开。用户可见的行为决定仍以设计访谈为准。

## 资源按内容复用

跨项目粘贴时，剪贴板冻结的 `library.assets` 与目标项目 `mapping_assets` 中同 ID 的行，只有在 name、mime 与 sha256 完全一致时才复用目标 ID；否则在目标项目新建 Asset 并统一改写正文图片块与独立图片的引用，不覆盖目标项目已有内容。指纹算式统一为 `backend/src/mapping/media.ts` 的 `assetHash(bytes)`，写入与比对共用。目标行缺少可信 hash 时按「不可复用」处理，不静默沿用。

## 目标动作与源状态隔离

- **同项目粘贴**：读取当前项目的 `cutState`；`eligible` 走 `canvas.paste-cut` 恢复原对象身份与仍有效的外部连线（D466）。记录缺失或无权访问时明确报告，不写目标。
- **异项目粘贴**：不读取源项目的 `cutState`。剪贴板已冻结完整子树、标签与资源；源记录缺失、源项目权限回收或源项目不可访问都不阻止目标写入。目标项目的权限由 `Mapping.execute` 承担。依据 AC1「target paste 形成各自项目动作」与 AC3「不……联动删另一边」。
- 目标写入只写目标项目，不消耗、不改写源项目的剪切资格与历史。

## 目标请求的持久恢复

- 仅**跨项目 cut 来源**的粘贴写 `forkwise.paste-pending.v1:<projectId>`。普通副本、外部文本与回源项目的粘贴不写；未确认记录也只阻断同一类请求，不误伤无关粘贴。
- 发送前保存最终完整命令（含 `action()` 补入的 `placement.expected`、冻结资源、落点与全部目标 ID）；写失败立即中止目标提交，源内容仍可从源项目历史恢复（AC4）。
- 受理回执后按精确 `commandId` 清理；刷新或重开后按原 `commandId`、原载荷重放，不重新解析剪贴板、不生成新 ID（D467）。
- **拒绝分类按响应出口，不按业务错误码清单**：`execute` 只有两个「结果未知」出口——未知异常的兜底 503 `SAVE_FAILED`，以及无响应码的传输层故障（API 层补 `UNAVAILABLE`）。其余响应都是 `DomainError` 业务拒绝，事务已回滚、确定未提交；**包括 `SNAPSHOT_UNAVAILABLE` 这类 503**（创建序位读取发生在事务持久化之前），不能与兜底 503 混为一类，否则会永久保留记录并锁死该项目的跨项目粘贴。首次发送的任何业务拒绝都可确认未提交（命令编号此前从未发出）；重放时 401／403 权限检查在幂等回执查询之前，仍按结果未知保留。
- 解析类 400 虽在回执查询之前，但对**本机持久化的同一份载荷**解析结果确定，能证明请求从未进入事务，故重放亦可确认未提交。CONTRACT §2 的「严格解析 → 查 commandId」顺序正是该确定性的来源，不是冲突；若把解析类一律按结果未知保留，无效载荷会永久锁死粘贴。
- 页面内「重试保存」沿用同一 `commandId`，属重放而非首次发送；`action()` 按是否已有 pending 请求选择 `first`／`replay`，权限回收时不会误清恢复记录。
- 服务端新增或改名业务拒绝码自动落进正确分支，无需前后端同步清单。两个「结果未知」码由 `backend/src/mapping/recovery-contract.ts` 单一来源导出，`http.ts` 的兜底响应、`api.ts` 的无响应兜底与 `paste-recovery.ts` 的分类共用同一常量；改动兜底出口只需改这一处。恢复记录按项目隔离，与源项目的 `cutJournal` 分开保存、互不覆盖；清理只删除精确匹配的 `commandId`。

## 明确排除与已知边界

- `paste-pending` 是本机临时恢复记录，不是项目领域数据：**不进导出／导入、备份或投影**，也不做跨设备同步、自动重试频率或后台轮询（D467）。完整命令含 base64 资源，写入 localStorage 存在配额风险；写失败按上文中止，超大载荷上限未验证。
- AC2「批注与容器的后交付适配按共用约定闭合」：容器半边已由 `emptiedGroups`／`emptiedGroupKeys` 的共用判定闭合；随动批注（Attachment）在 `backend/src/mapping` 尚无实现，属**后交付方待闭合**。本票不能凭空新增领域类型来「闭合」尚不存在的能力，也不会伪造交叉兼容证据；该缺口在此明确登记，不伪装成已通过。
- 新增的是临时恢复记录而非领域类型，故不触发「序列化／导入导出／备份／投影及相关入口」的适配要求；定位与排除理由如上。
- `PasteRecovery` 与 `cutJournal` 的薄存储适配同形但**不合并**：前者写失败必须抛错以中止目标提交，后者吞错由内存中的待处理请求负责重试，合并会把剪切语义带进粘贴。重放 effect 不复用 `action()`：它需要原始错误分类，且不能把未确认请求挂成 `pendingAction` 阻塞整个 UI。
- #33 第五轮证据修正（`frontend/tests/canvas-cut.spec.ts` 的 CDP 权限 probe、`ac.AC1`、`unverified`）随本票提交，属独立历史修正，不构成 #45 的功能范围；按「保护无关 WIP」保留，不回退，也不再改动其 probe 文本。本票对该文件只保留「跨项目剪切包边界」用例的断言改写。
- `emptiedGroupKeys` 是 `emptiedGroups` 的薄封装，但在删除计划两处与剪切捕获一处共三处复用，符合「不为单次使用抽 helper」的例外；测试 fixture 的 `push()` 用裸字典承载七类对象字段，是为消除七段重复的局部取舍，不进入生产类型。两者均为已披露的判断项，不作为新抽象扩张。
