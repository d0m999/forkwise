# 存储采用单文件 SQLite 与关系表

PRD 第 09 节明确不规定数据库，而本领域模型要求版本链、论证溯源、四种时间字段并存、按研究时点回看以及整体导出 JSON，这些能力恰好不是图数据库的强项。PRD 第 11 节提出每项目 100 份材料、1,000 页可解析文本、100 个节点与 150 条边作为可调建议，实际容量仍待验证，且 D01 已定首版只服务本人研究流程，不存在多用户并发写。决定采用单个 SQLite 文件加关系表（节点表、边表、版本表与各类关联表）承载全部图谱与审计数据，由 `better-sqlite3` 13.0.3 做同步驱动，`drizzle-orm` 0.45.3 负责 schema 定义与迁移，双时间查询与图遍历这类复杂查询直接写参数化 SQL 而不经过 ORM 抽象。相较图数据库方案（遍历与路径表达是原生能力，但版本、双时间回看、审计与整体导出都要自建，且需要额外常驻服务，对单人工具是不划算的运维负担），关系表的代价是路径遍历要自己写递归 CTE、schema 演进要写迁移；相较文档存储方案（写入形状自由、天然接近导出格式），文档存储的代价是双时间谓词与图遍历全部落到应用代码、缺少事务与并发保护、单文件 JSON 有损坏风险，这三项正是本项目最容易出错的地方。普通时点视图的内容有效区间与获取时间在 SQL 层统一过滤；完整历史判断另按 D36 保存的版本引用清单回放，不以当前对象或单一时点查询替代。备份与导出分别采用一致性快照及完整研究资产序列化，也让 FTS5 的 `trigram` 分词可以直接提供中文子串检索而无需引入独立搜索服务。影响是：写路径的并发能力被限制为单写者，这与单用户范围一致；若日后需要多机并发写，须另立 ADR 迁移到 PostgreSQL 而不是在本方案上打补丁。

启用项：`PRAGMA journal_mode=WAL`、`foreign_keys=ON`；FTS5 以 `trigram` 分词建立外部内容表，覆盖节点版本正文与证据原文片段。

## 影响

- 普通时点视图统一执行领域模型第 8.2 节的时间与分支作用域校验；完整历史判断读取当次保存的内容、材料、识别文本、立场及评估版本清单（D36）。
- 备份与「整体导出 JSON」是两条独立路径：前者通过在线备份 API 生成一致性数据库快照，并归档有权保存的原文与快照目录，后者按第 12 节的键清单序列化，二者互不依赖（ADR 0015）。
- 迁移脚本必须可回放；`revisions` 与其他审计表在任何迁移中只允许新增列，不允许改写既有行。
