# 后端采用 Node + Hono，以 OpenAPI 作为前后端唯一契约

材料解析、模型调用与数据库读写都必须发生在浏览器之外：API 密钥不能下发到前端，PDF 解析与长任务不能占用交互线程，S01 也要求服务端访问控制不能只依赖前端隐藏。同时首版只有一位使用者（D01），不需要多租户、消息队列或独立网关。决定后端采用 Node.js 22.22.2（本机已安装）加 TypeScript 5.9.3，Web 框架用 Hono 4.13.12，请求校验用 Zod 4.6.5，接口契约由 `@hono/zod-openapi` 1.6.3 生成 OpenAPI 3.0 文档，端点一律带 `/api/v1/` 前缀，统一响应形状为 `{code, data, message}`。相较引入 Python FastAPI（AI 生态与 PDF 工具链更成熟），代价是要维护第二套运行时与两套依赖，而本项目的解析与抽取在 Node 侧已有可用方案（ADR 0013、0014），单进程内完成解析、抽取与落库能省掉跨进程任务编排；相较 Express 或 NestJS（生态更大或分层更重），NestJS 的依赖注入与模块体系对单人工具的规模是过度设计，Express 则需要另配校验与文档生成。这一选择的代价是：Hono 的中间件生态不如 Express 丰富，遇到小众集成要自己写适配；单进程架构意味着长任务只能在进程内排队，任务吞吐上限受单机限制。影响是：目录严格分层为 routers / controllers / services / repositories，依赖只向下，单文件不超过 300 行，入口只做装配；`openapi.yaml` 由代码生成并提交进仓库，前端据此生成 TypeScript 类型与 mock，后端据此实现，任何端点变更必须先改 schema 再改代码。

## 接口约束

- 所有读图端点接受可选 `asOf` 参数，缺省为当前时刻；回看结果不得写回任何时间字段（领域模型 8.2）。
- 修改既有对象的变更端点接受 `expected_target_version`，版本不符返回 409 且不应用变更（M03、D92）；多对象操作同时校验该操作所依赖的相关对象版本，具体请求形状继续设计。
- 所有写端点接受 `Idempotency-Key` 请求头，命中即返回既有结果（N02）。
- 服务端绑定回环地址，会话令牌只在本地发放；首版不实现注册、邀请与分享（S01）。
- 错误响应必须带可解释的 `message`，禁止把「未知」「不可比」折叠为「未满足」（领域模型 9.1）。
- 日志不得记录完整敏感原文（S02）。

## 研究内容按业务操作写入（2026-10-06 确认）

本人确认：研究内容采用按具体业务操作提交的写入方式。前端提交新建、改写、连接、重接、保存立场或删除等操作所需的目标与参数；修改既有对象时携带预期版本，后端负责校验、事务及该操作应有的版本和历史记录。画布与 D90 的列表视图操作同一套研究对象，复用相同的业务写入规则。

相较沿用原型的整份工作区快照保存，这一选择需要逐项定义操作契约，但能明确修改范围、版本冲突和历史生成责任；整份工作区快照不作为日常研究内容的覆盖写入接口。布局与研究内容分别保存，位置、颜色等布局修改不生成研究内容版本，布局可合并批量提交。

本项确定写入粒度，不锁定端点路径、请求 DTO 或具体数据库表结构；响应范围按下节决定，导出与恢复另按各自契约处理。本决定是已确认设计，尚未接入生产后端。

## 日常操作返回完整变化集合（2026-10-06 确认）

本人采用：日常研究操作成功后，返回本次操作的完整受影响对象集合，包括连带变化及删除 ID；首次打开研究或冲突恢复时，读取当前项目的完整研究状态。写入仍按具体业务操作提交。

变化集合须覆盖同一次操作导致的全部新增、更新与删除，不能只返回直接操作的目标。前端使用配套版本信息校验变化集合，并整批应用到共享研究状态，让画布与列表读取同一批结果；校验不通过时进入完整读取与冲突恢复，不应用其中一部分。

相较每次写入都返回完整研究状态，这一选择减少日常响应中的重复数据，但要求后端准确收集连带变化，前端正确处理版本和整批更新。该选择基于处理范围的架构判断，尚无实际性能压测；对象版本与项目修订号的职责按下节决定，具体响应 DTO 与恢复细节继续逐条设计，尚未接入生产后端。

## 对象版本控制写入冲突，项目修订号控制变化同步（2026-10-07 确认，D92）

本人采用：界面与已授权外部 Agent 复用同一套版本规则。对象版本用于判断提交所依据的对象是否已改变，项目修订号用于判断客户端是否漏掉研究状态变化；项目修订号不作为日常操作的全项目写入冲突条件。修改无关联的 A、B 对象时，两次操作可分别成功；根据同一旧版本修改 A 时，先提交者成功，后提交者收到 409，后一次操作不写入，保留草稿供重新读取与本人处理。

涉及共享前提、推导关系或删除的操作，在同一事务内校验相关对象版本、作用范围及图谱规则；不能只检查直接目标而忽略操作所依据的关联对象。结构规则按提交时的一致状态检查，包括防环与避免悬空关系；任何校验失败均不部分写入。对象版本表示写入依据，不与内容历史、材料版本或已记录历史判断混为同一编号。

项目完整读取返回与该状态一致的项目修订号。日常成功响应返回完整变化集合及这次变化前后的项目修订号；客户端仅在可与本地状态衔接时整批应用。无法衔接时不部分应用变化，重新读取项目完整状态，并保留未提交草稿进入恢复流程。画布、列表与 MCP 遵循同一契约。

相较用一个项目版本拒绝所有旧项目状态的写入，这一选择允许无关联对象分别修改，同时避免漏掉连带变化；代价是各业务操作须明确相关对象范围，并正确返回完整变化集合和修订号。具体字段名、对象内部版本划分、项目修订号覆盖范围、重复或乱序响应处理及草稿恢复交互继续设计。本项为已确认设计，尚未实现或完成并发、恢复及性能验证。
